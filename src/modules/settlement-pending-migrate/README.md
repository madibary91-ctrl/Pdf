# settlement-pending-migrate

CLIِ رسمیِ **نصبِ اختیاری، وضعیت، راستی‌آزمایی و برگشتِ** نمایهٔ «مرده‌های در انتظارِ تأیید» (م۳‑ه‑۴‑الف‑۲‑۴‑ب‑۲‑۱، ADR-0047؛ دستورِ `down`: ب‑۲‑۲‑۲، ADR-0049؛ خودِ نمایه: `settlement-pending`، ADR-0046).
سیاستِ SQL (TRIGGERها، backfill زیرِ قفل، نگهبان، دفترِ مهاجرتِ جدا) در `settlement-pending` می‌ماند؛ این ماژول فقط **ترتیب، پیش‌بازرسی، راستی‌آزمایی، مهلت و گزارش** دارد.
به `process`، `pg`، drizzle، ساعتِ سیستم و `console` مستقیم وابسته نیست؛ همه تزریقی است (گلوی `tooling/cli/settlement-pending-migrate.ts` آن‌ها را می‌دهد). هیچ SQLی ندارد.

## استفاده
```
DATABASE_URL=… npm run settlement:migrate -- up                       # پیش‌نیاز (ADR-0034)
DATABASE_URL=… npm run settlement:pending -- status                   # فقط‌خواندنی؛ خروج ۳ اگر نصب نشده/معلق باشد
DATABASE_URL=… npm run settlement:pending -- up --timeout-ms=120000   # نصبِ اختیاری و idempotent + راستی‌آزمایی
DATABASE_URL=… npm run settlement:pending -- verify                   # سنجشِ سنگینِ نمایه در برابر حقیقت؛ خروج ۹ اگر ناهمخوان
DATABASE_URL=… npm run settlement:pending -- down --yes               # برگشتِ رسمیِ نصب (ADR-0048/0049)؛ بی‌--yes خطای آرگومان (۲)
```
شِما فقط از env: `SETTLEMENT_OUTBOX_SCHEMA` (همان برنامه؛ نبودن/خالی = پیش‌فرض). **با همان فایلِ envِ برنامه می‌شود اجرا کرد**: متغیرهای پایشِ پسماند (`SETTLEMENT_BACKLOG_WATCH`، `SETTLEMENT_BACKLOG_SOURCE` (ADR-0051؛ مقدارش اینجا نادیده است) و آستانه‌ها) شناخته‌اند (`settlement-migrate` آن‌ها را رد می‌کند؛ ADR-0047 یافتهٔ ۱). با `node --env-file=.env` هم می‌شود (CLI خودش `.env` نمی‌خواند). Node ≥ ۲۲٫۱۸.

**نصب اختیاری و بی‌اثر بر برنامه است:** تا `up` نزنید هیچ‌چیز در settlement عوض نمی‌شود. پس از `up` هر نوشتنِ `dead`/تأیید یک درج/حذفِ اضافه در همان تراکنش می‌گیرد (TRIGGER روی جدول‌های پول؛ ADR-0046). **الگوی نصب:** پنجرهٔ کم‌ترافیک ← `status` ← `up` ← (خودکار verify) ← `status`. اگر `up` خروج ۱۰ داد (قفل در ۱۵ثانیه به دست نیامد)، چیزی عوض نشده؛ بعداً دوباره بزنید.

## `down` — برگشتِ رسمی (ADR-0049)
`down --yes` همهٔ مهاجرت‌های اعمال‌شدهٔ نمایه را با `PendingDeadIndex.down()` (ADR-0048) در یک تراکنش برمی‌دارد؛ پس از آن پایگاه مثلِ پیش از نصب است، `status` ⇒ ۳ و `verify` ⇒ ۳، و `up` دوباره نصب می‌کند. **به رکوردهای outbox/تأیید (حقیقتِ مالی) دست نمی‌زند**؛ فقط نمایهٔ مشتق می‌رود.
- **تأییدِ صریح:** `--yes` فقط برای `down` معنا دارد (بی‌مقدار، تک‌بار). بی‌آن (یا `--yes` با دستورِ دیگر) خطای آرگومان است ⇒ ۲ بی‌اتصال؛ تایپِ تصادفیِ دستورِ مخرب هرگز DDL نمی‌زند.
- **جریان:** `check` (فقط‌خواندنی) ← اگر چیزی اعمال نشده ⇒ **۰ بی‌کار و بی‌قفل** (`down()` صدا زده نمی‌شود) ← `down()` (بازتلاشِ فقط برای بن‌بست) ← بازخوانیِ دفتر: **باید خالی باشد** وگرنه ۶ (هرگز «ok» بر پایهٔ ادعای `down()`).
- **نگاشتِ خطا (همان `up`):** `55P03` ⇒ ۱۰ (قفل در ۱۵ثانیه به دست نیامد؛ چیزی عوض نشده؛ **هرگز خودکار تکرار نمی‌شود**: `down` خواننده‌های outbox را هم کوتاه بلوک می‌کند) · وابستگیِ شیءِ بیرونی (`2BP01`، مثلاً view) ⇒ ۶ با `pgCode` و برگشتِ کاملِ تراکنش (نصب سالم می‌ماند؛ view را بردارید و دوباره بزنید) · دفترِ دست‌کاری/ناشناخته ⇒ ۵ پیش از هر DDL · نبودنِ جدول‌های settlement با دفترِ نمایه ⇒ ۸ · مهلت ⇒ ۷.
- **برگشتِ هم‌زمان:** دو `down` هم‌زمان هر دو ۰ می‌دهند (برنده برمی‌دارد، بازنده بی‌کار است؛ تشخیصِ «نبودنِ واقعیِ جدول‌ها» از «برگشتِ دیگری» با بازخوانیِ دفتر، ناوردا ۱۰ در `execute.ts`).
- **گزارش:** `migrations` = `{applied, pending, appliedNow: [], revertedNow}`؛ `verify` نمی‌آید (نمایه دیگر نیست).
- **مهلت/SIGTERM:** فرایند می‌میرد و برگشتِ نیمه‌کار هرگز اعمال نمی‌شود (آزمونِ فرایندِ واقعی).
- **الگوی برگشت:** پنجرهٔ کم‌ترافیک ← `status` ← `down --yes` ← `status` (⇒ ۳). اگر خروج ۱۰ بود، چیزی عوض نشده؛ بعداً دوباره بزنید. نصب روی تولید همچنان مشروط به اندازه‌گیریِ backfill در مقیاسِ واقعی (ب‑۲‑۴) و بازبینیِ انسانی است.

## کدهای خروج (۰ تا ۷ هم‌معنا با `settlement-migrate`)
| کد | نام | معنا |
|---|---|---|
| ۰ | `OK` | status: نصب و به‌روز · up: موفق یا کاری نبود · verify: نمایه با حقیقت می‌خواند |
| ۱ | `INTERNAL` | خطای برنامه‌نویسی/پورتِ خراب/شکلِ ناشناختهٔ پاسخ (بسته: هرگز «خوب» نمی‌شود) |
| ۲ | `USAGE` | آرگومان یا env نامعتبر؛ **هیچ اتصالی ساخته نشد** |
| ۳ | `PENDING` | status/verify: نمایه نصب نشده یا ناقص است (پس از موفقیتِ `down` همین است) |
| ۴ | `UNAVAILABLE` | پایگاه در دسترس نیست؛ هیچ تغییری اعمال نشد |
| ۵ | `SCHEMA_MISMATCH` | دفترِ مهاجرتِ نمایه با کد نمی‌خواند؛ **هیچ تغییری اعمال نشد** |
| ۶ | `MIGRATION_FAILED` | up/down در apply یا راستی‌آزماییِ وضعیت شکست خورد (تراکنشِ apply برگشته؛ تکرار امن است؛ در `down` وابستگیِ بیرونی `2BP01` هم همین است) |
| ۷ | `TIMEOUT` | مهلتِ کل یا سقفِ زمانِ سمتِ پایگاه (57014) گذشت |
| ۸ | `PREREQUISITE` | جدول‌های outbox/تأیید نیستند؛ ابتدا `settlement:migrate up`. هیچ تغییری اعمال نشد |
| ۹ | `INCONSISTENT` | verify (یا راستی‌آزماییِ پس از up) `missing`/`stale` > ۰ یافت. **پس از up یعنی نصب پذیرفته نیست** (نصب ماندگار است؛ گزارش `appliedNow` را دارد) |
| ۱۰ | `LOCK_BUSY` | backfill (یا `down`) در ۱۵ثانیه قفلِ نویسنده‌ها را نگرفت (55P03)؛ تراکنش برگشت. **خودکار تکرار نمی‌شود** |

## گزارش (stdout، دقیقاً یک خطِ JSON؛ stderr خالی)
`{tool, command, ok, code, exitCode, phase?, pgCode?, migrations?, verify?, retries?, issues?, usage?, closed?}` — `migrations` = `{applied, pending, appliedNow}`؛ `verify` = `{consistent, expected, indexed, missing, stale}` (فقط شمارش)؛ `phase` ∈ `check|apply|verify`؛ `closed:false` یعنی بستنِ اتصال شکست/به مهلت خورد. هیچ مقدارِ env، رشتهٔ اتصال، شِما یا متنِ خطای پایگاه در گزارش نیست؛ `pgCode` فقط SQLSTATEِ پنج‌نویسه.

## ناورداها
- **check پیش از هر نوشتن**؛ ناهمخوانی/در دسترس‌نبودن ⇒ هیچ مهاجرتی نیست. **بی‌کاری = بی‌نوشتن و سبک** (up روی نصبِ کامل verify سنگین نمی‌زند).
- **راستی‌آزماییِ دو‌لایه پس از اعمال:** وضعیتِ دفتر دوباره خوانده می‌شود و سپس نمایه در برابر حقیقت سنجیده می‌شود؛ `consistent` ی ادعاییِ فروشگاه از شمارش‌ها **دوباره محاسبه** می‌شود (ادعای ناسازگار ⇒ ۱).
- **بازتلاش فقط برای بن‌بست/ناسازگاریِ سریال‌سازی** (`40P01`، `40001`؛ حداکثر ۳ تلاش). `55P03` و هر خطای دیگر **هرگز** تکرار نمی‌شود: هر تلاشِ backfill نویسنده‌های پول را دوباره در صف می‌گذارد.
- **مهلتِ کل** با زمان‌سنجِ تزریقی؛ پس از مهلت هیچ فراخوانیِ تازه‌ای (از جمله migrate) به فروشگاه نیست. `--timeout-ms` همزمان **سقفِ زمانِ سمتِ پایگاهِ verify** هم هست (پرسشِ رهاشده در پایگاه نمی‌ماند). گلو `lock_timeout`/`statement_timeout` ی ۶۰۰ثانیه‌ای روی اتصال می‌گذارد (backendِ «زامبی» کران‌دار)؛ `lock_timeout` ی ۱۵ثانیه‌ایِ backfill درونِ مهاجرت بر آن غالب است.
- **ورودی:** دستور (`status|up|verify|down`)/فلگِ ناشناخته و تکراری خطاست؛ آرگومانِ موضعی هرگز پژواک نمی‌شود؛ هر `SETTLEMENT_*`ِ ناشناخته خطاست؛ `DATABASE_URL` فقط حضورش سنجیده می‌شود؛ نوعِ هر دو متغیرِ شِما سنجیده می‌شود.
- **تنبل:** آرگومان/شِمای نامعتبر هرگز اتصالی نمی‌سازد.

## محدودیت‌ها
پیام‌های خطای آرگومانِ قفل‌شدهٔ ۰۰۴۷ («status، up یا verify») هنوز `down` را نام نمی‌برند (آزمون‌های قفل‌شده عینِ متن را می‌خواهند)؛ فهرستِ درست در `USAGE` و این README است. `PendingMigratable.down` در نوع اختیاری است (فروشگاه‌های ساختگیِ ۰۰۴۷)؛ نبودنش در `down` ⇒ ۱. `down()`ِ کتابخانه زیرِ هم‌زمانی روی اتصالِ گرم ممکن است `NOT_MIGRATED` (42P01) بدهد؛ CLI آن را با بازخوانیِ دفتر درست تفسیر می‌کند (ADR-0049 یافتهٔ ۱). فقط نمایهٔ `settlement-pending` را می‌شناسد. ابزارِ تعمیرِ نمایه نیست (عمداً: `up` روی نصبِ ناهمخوان بی‌کار است و تشخیص با `verify`). `verify` سنگین است (O(مرده‌ها + تأییدها)). `deadline.ts` و `lazy-database.ts` کپیِ آگاهانهٔ `settlement-migrate` است (آزمونِ tooling همسانی را قفل می‌کند). سیم‌کشی به bootstrap/پایش برشِ بعد است. فقط Node ≥ ۲۲٫۱۸.
