# راهنمای استقرارِ نقش‌های سیاستِ ابزار (migrate ← نقش ← grants ← verify ← برنامه)

> مرجع: ADR-0080 (مهاجرت)، ADR-0081 (حقوق)، ADR-0082 (این راهنما و اثباتِ میزبان با نقشِ واقعی).
> هر جملهٔ «اجرایی» این راهنما را آزمونِ `tooling/tool-policy-roles-runbook.test.ts` با کد می‌سنجد (کدهای خروج، نامِ اسکریپت‌ها، نامِ envها، ترتیبِ گام‌ها)،
> و رفتارِ میزبان با نقشِ بی‌امتیازِ واقعی را `tooling/tool-policy-bootstrap-role.pg.test.ts` روی PostgreSQL واقعی ثابت کرده است.

## ۱) اصل‌ها
1. **دو نقش، دو کار.** نقشِ مهاجرت/مدیر (مالکِ شِما؛ DDL) فقط در استقرار؛ نقشِ زمانِ اجرا (کمترین امتیاز) فقط در برنامه. هرگز یک نقش برای هر دو.
2. **ابزارها نقش نمی‌سازند و رمز نمی‌گیرند.** `CREATE ROLE` و رمز کارِ مدیرِ پایگاه است؛ رمز در مخزن، لاگ، یا خطِ فرمان (تاریخچهٔ شل) نمی‌ماند. رشتهٔ اتصال فقط از محیطِ فرایند (مدیریتِ اسرارِ استقرار) می‌آید.
3. **دروازهٔ استقرار `verify` است، نه میزبان.** میزبان فقط می‌خواند و حقِ زیاد را نمی‌بیند (بند ۴)؛ پس بدونِ `verify` با کدِ خروجِ ۰ نباید ترافیک به برنامه برسد.

## ۲) ترتیبِ استقرار (همیشه همین ترتیب)
| گام | که | فرمان | شرطِ عبور |
|---|---|---|---|
| ۱ | نقشِ مهاجرت | `DATABASE_URL=<migrate-url> npm run policy:migrate -- up --create-schema` | کدِ خروجِ ۰ (شِما را فقط با فلگِ صریحِ `--create-schema` می‌سازد) |
| ۲ | مدیرِ پایگاه | `CREATE ROLE policy_runtime LOGIN PASSWORD '<از مدیریتِ اسرار>'` (بی‌`SUPERUSER`/`CREATEROLE`/`CREATEDB`/`BYPASSRLS`/`REPLICATION`؛ و **مالکِ** هیچ شیئی نباشد) | نقش وجود دارد |
| ۳ | مدیر/بازبین | `npm run policy:grants -- plan --role=policy_runtime` | دستورها بازبینی شد (بی‌اتصال؛ چیزی اجرا نمی‌شود) |
| ۴ | نقشِ مهاجرت | `DATABASE_URL=<migrate-url> npm run policy:grants -- apply --role=policy_runtime` | کدِ خروجِ ۰ (همگرا: `REVOKE ALL` سپس `GRANT` دقیقاً قرارداد؛ دوباره می‌خواند) |
| ۵ | نقشِ مهاجرت | `DATABASE_URL=<migrate-url> npm run policy:grants -- verify --role=policy_runtime` | **کدِ خروجِ ۰ — دروازه** |
| ۶ | برنامه | `TOOL_POLICY_HOST=on` + پنج عددِ تنظیم (بند ۵) | `GET /api/health/policy/ready` ← ۲۰۰ |

اگر `TOOL_POLICY_SCHEMA` سفارشی است، همان را به هر دو CLI و برنامه بدهید. گام‌های ۱، ۴، ۵ idempotent‌اند و با هر استقرار تکرار می‌شوند (مهاجرتِ تازه ⇒ `verify` اگر قرارداد عقب باشد قرمز می‌شود).

## ۳) قراردادِ حقوقِ نقشِ زمانِ اجرا
| شیء | حقِ مجاز | هر حقِ دیگر |
|---|---|---|
| شِما | `USAGE` | خطا (`CREATE` هرگز) |
| `tool_policy_versions` | `SELECT` + `INSERT` | خطا (`UPDATE`/`DELETE`/`TRUNCATE`/`REFERENCES`/`TRIGGER` هرگز) |
| `tool_policy_migration_ledger` | فقط `SELECT` | خطا |
میزبانِ سیاست (`tool-policy-bootstrap`) فقط می‌خواند؛ `INSERT` را مسیرِ ثبتِ نسخهٔ مدیر (`append`) لازم دارد. ثابت‌شده: بی‌`INSERT` میزبان ۲۰۰ است ولی `verify` آن را `missing:tool_policy_versions:INSERT` می‌گوید.

## ۴) کدهای خروجِ `policy:grants`
| کد | نام | معنا و اقدام |
|---|---|---|
| 0 | OK | دقیقاً قرارداد. |
| 1 | INTERNAL | خطای داخلی؛ گزارش کنید (متنِ خطا عمداً چاپ نمی‌شود). |
| 2 | USAGE | آرگومان/محیطِ نامعتبر. |
| 3 | PENDING | شِما/جدول‌ها مهاجرت نشده‌اند؛ گام ۱. |
| 4 | UNAVAILABLE | پایگاه/اتصال در دسترس نیست؛ بعداً تکرار کنید. |
| 5 | DRIFT | حقِ کم (`missing:…`) یا حقِ زیاد (`excess:…`)؛ `apply`. |
| 6 | APPLY_FAILED | حقِ ناحذف‌شدنی (PUBLIC یا عضویتِ نقشِ دیگر)؛ ریشه را مدیر بردارد. |
| 7 | TIMEOUT | مهلت؛ چیزی اعمال نشده؛ با `--timeout-ms` بیشتر تکرار کنید. |
| 8 | ROLE_UNUSABLE | نقشِ ناموجود/خطرناک/مالک؛ **هیچ چیز نوشته نشد**؛ نقش را درست بسازید. |

## ۵) محیطِ برنامه
`TOOL_POLICY_HOST` ← فقط `on` روشن می‌کند (پیش‌فرض خاموش). با `on` این پنج متغیر **الزامی و بی‌پیش‌فرض‌اند** (پنجرهٔ تازگی تصمیمِ مالکِ محصول است):
`TOOL_POLICY_INTERVAL_MS`، `TOOL_POLICY_RETRY_MS`، `TOOL_POLICY_ATTEMPT_DEADLINE_MS`، `TOOL_POLICY_REFRESH_TIMEOUT_MS`، `TOOL_POLICY_MAX_STALE_MS`.
اختیاری: `TOOL_POLICY_SCHEMA`، `TOOL_POLICY_STATEMENT_TIMEOUT_MS`، `TOOL_POLICY_SHUTDOWN_TIMEOUT_MS`، `TOOL_POLICY_BOOT_ATTEMPTS`، `TOOL_POLICY_BOOT_RETRY_DELAY_MS`. جزئیاتِ بازه‌ها: README ماژولِ `src/modules/tool-policy-bootstrap/README.md`.

## ۶) عیب‌یابی: میزبان آماده نمی‌شود
| نشانه (لاگِ `bootstrap`/پروبِ `ready`) | معنا | اقدام |
|---|---|---|
| `NOT_MIGRATED` (یک تلاش، بی‌بازتلاش) | شِما یا جدول‌ها نیستند — حتی برای نقشِ بی‌حق | گام ۱ |
| `UNAVAILABLE` با **همهٔ** تلاش‌های `TOOL_POLICY_BOOT_ATTEMPTS` | یا پایگاه واقعاً در دسترس نیست، **یا نقش یکی از سه حقِ خواندن را ندارد** (محدودیتِ شناخته‌شده: میزبان خطای مجوز را از قطعیِ گذرا جدا نمی‌کند) | **`verify` را اجرا کنید**: `missing:…` حقِ گمشده را نام می‌برد؛ سپس `apply` |
| `ready` از ۲۰۰ به ۵۰۳ می‌افتد، `live` ۲۰۰ می‌ماند | سیاست کهنه شد (`MAX_STALE_MS`)؛ از جمله وقتی حقِ `SELECT` در حینِ اجرا لغو شده | `verify` ← `apply`؛ **بی‌ری‌استارت** خودبه‌خود به ۲۰۰ برمی‌گردد (ثابت‌شده) |
| `verify` ⇒ ۵ با `excess:…` | حقِ زیاد؛ میزبان آن را نمی‌بیند ولی قرارداد نقض است | `apply` |

## ۷) محدودیت‌های صادقانه (باز؛ ADR-0082)
- **میزبان از استخرِ مشترکِ `@/db` (همان `DATABASE_URL`ِ کلِ برنامه) می‌خواند.** پس «برنامه با نقشِ بی‌امتیاز» فقط وقتی ممکن است که کلِ برنامه همان نقش را بگیرد، که نمی‌شود (جدول‌های دیگر حقوقِ دیگر می‌خواهند). تا برشِ «استخرِ اختصاصیِ سیاست» (رشتهٔ اتصالِ جدا برای میزبانِ سیاست) نیامده، قراردادِ این راهنما با نقشِ واقعی آزموده و ثابت شده ولی **اتصالِ تولیدیِ میزبان هنوز با آن نقش وصل نیست**.
- میزبان به دروازهٔ ابزار وصل نیست (فقط سلامت/تازگیِ سیاست دیده می‌شود).
- خطای مجوز در میزبان کدِ جدا ندارد (جدولِ بند ۶)؛ افزودنِ آن تغییرِ قرارداد در چند ماژول است و نیازمندِ تأییدِ معماری.
- `MAINTAIN` (PostgreSQL ≥ ۱۷)، `ALTER DEFAULT PRIVILEGES` و حقوقِ سطحِ پایگاه پوشش داده نشده؛ آزمون‌ها فقط روی PostgreSQL ۱۵ اجرا شده‌اند.
